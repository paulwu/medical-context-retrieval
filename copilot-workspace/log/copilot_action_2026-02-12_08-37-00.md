### Root Cause Correction

**Session 10 was wrong.** The `networkingMode=mirrored` was NOT the root cause. The error persists with `networkingMode=nat` after a full WSL restart.

**Actual root cause:** The HvSocket pipe between VS Code (Windows) and WSL2 VM breaks after ~16 seconds during DevContainer rebuild. Docker exec works fine when run from within WSL itself (tested: 20 seconds continuous without issue). The pipe break is specific to the `wsl.exe -e /bin/sh` session that the Dev Containers extension creates.

**Contributing factor:** WSLg (GUI support) creates additional HvSocket connections (Weston compositor, PipeWire audio, X11/Wayland forwarding) that compete with the shell pipe for HvSocket bandwidth on Windows Insider build 26200.

## Changes Made

### 1. `.wslconfig` — Disable WSLg GUI support

**Before:**
```ini
[wsl2]
memory=24GB
processors=16
swap=8GB
networkingMode=nat
```

**After:**
```ini
[wsl2]
memory=24GB
processors=16
swap=8GB
networkingMode=nat
guiApplications=false
localhostForwarding=true
```

- `guiApplications=false` — Disables Weston compositor, PipeWire audio, and Wayland/X11 forwarding. This eliminates 3-4 HvSocket connections that compete with the VS Code shell pipe. DevContainers don't need GUI support.
- `localhostForwarding=true` — Ensures Docker TCP port (2375) is accessible from Windows localhost.

### 2. Docker daemon — TCP listener on localhost:2375

Created `/etc/systemd/system/docker.service.d/tcp-override.conf`:
```ini
[Service]
ExecStart=
ExecStart=/usr/bin/dockerd -H fd:// -H tcp://127.0.0.1:2375 --containerd=/run/containerd/containerd.sock
```

- Docker now listens on both unix socket AND TCP 127.0.0.1:2375
- TCP access verified working: `docker -H tcp://127.0.0.1:2375 info` ✓
- Enables future Docker Desktop-free Docker access from Windows (if docker.exe installed)

### 3. WSL environment — DOCKER_HOST in .bashrc

Added `export DOCKER_HOST=tcp://127.0.0.1:2375` to `~/.bashrc` so Docker CLI defaults to TCP access within WSL.

### 4. `.devcontainer/devcontainer.json` — stability improvements

- Added `"initializeCommand": "docker info > /dev/null 2>&1 && echo 'Docker ready'"` — pre-warms Docker daemon before build starts
- Added `"waitFor": "updateContentCommand"` — reduces the time window during which the fragile WSL shell pipe must stay alive
- Added `"containerEnv": { "DOCKER_HOST": "unix:///var/run/docker-host.sock" }` — explicit Docker socket path inside container

### If rebuild still fails (escalation path)

**Option A: Install Docker CLI on Windows for direct TCP access**
```powershell
# From PowerShell (admin)
winget install Docker.DockerCli
# Or download from: https://download.docker.com/win/static/stable/x86_64/
```
Then in VS Code User Settings (JSON):
```json
"docker.host": "tcp://localhost:2375"
```
This bypasses the WSL shell pipe entirely for Docker operations.

**Option B: Downgrade to stable Windows build**
Windows Insider Preview build 26200 has known WSL2 stability issues. Using a stable Windows release (e.g., 24H2) eliminates the HvSocket pipe instability.

**Option C: Use Docker Desktop for Windows**
Docker Desktop manages its own stable connection to WSL2 and doesn't rely on `wsl.exe` shell pipes.
