### The Docker daemon confirms: the pipe breaks FROM THE CLIENT SIDE

```
Error running exec 2e50baef... in container: exec attach failed: error attaching stderr stream: write unix /run/docker.sock->@: write: broken pipe
```

This means:
1. The Docker daemon tried to write to the docker exec session's stderr
2. The client-side (docker CLI running in VS Code's WSL shell) had already disconnected
3. The client disconnected because the WSL shell died

### Why the WSL shell dies: the pipe between Windows VS Code and WSL2 VM breaks

The VS Code Dev Containers extension runs all Docker commands through a WSL shell:
```
wsl -d Ubuntu -e /bin/sh -c cd '...' && /bin/sh
```

This shell communicates with VS Code via a Windows named pipe. After ~14.6 seconds (consistent across all 5 failures), this pipe breaks, causing the shell to receive EOF on stdin and exit normally (code 0).

The timing is consistent across all runs:
- Session 3: ~14s
- Session 6: ~5s (different — ENTRYPOINT issue, already fixed)  
- Session 7: ~14s
- Session 8: ~14.8s
- **Session 9: ~14.645s**

This is a **WSL2 transport layer issue**, not a DevContainer configuration problem.

## Changes Made

### `.devcontainer/devcontainer.json`

1. **Added `"userEnvProbe": "none"`** — The default `loginInteractiveShell` probe spawns `bash --login -i` inside the container at 08:12:45.038, just 27ms before all connections die at 08:12:45.065. This probe creates additional docker exec sessions and significant pipe traffic during the critical attachment window. Setting to `"none"` eliminates this entire operation, reducing pipe load and changing timing.

2. **Added `"updateRemoteUserUID": false`** — Eliminates the secondary Docker build step for UID remapping that generates the `InvalidDefaultArgInFrom` warning. The base image `mcr.microsoft.com/devcontainers/python:1-3.12-bookworm` already creates the `vscode` user with UID 1000, matching the WSL host user.
