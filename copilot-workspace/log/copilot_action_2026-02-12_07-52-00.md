## Root Cause

Despite the previous fix (adding `ENTRYPOINT ["sleep", "infinity"]` and `"overrideCommand": false`), the container still dies ~5 seconds after starting. The log reveals the Dev Containers CLI **always overrides the entrypoint** regardless of `overrideCommand`:

```
docker run ... --entrypoint /bin/sh vsc-...-uid -c echo Container started
```

This makes PID 1 = `/bin/sh -c "echo Container started"`, which exits immediately. The Dockerfile's `ENTRYPOINT ["sleep", "infinity"]` is completely ignored because `--entrypoint /bin/sh` takes precedence.

With `overrideCommand: false`, the CLI does NOT inject its own keep-alive loop, and the Dockerfile ENTRYPOINT is overridden anyway. Result: PID 1 exits → container stops → all exec sessions die → "unexpected end of parent stream".

**The correct fix:** Remove `overrideCommand: false` so it defaults to `true`. This makes the CLI inject `while sleep 1000; do :; done` as PID 1, keeping the container alive independently.

## Summary

The previous fix was based on the assumption that `overrideCommand: false` would make the CLI honor the Dockerfile's ENTRYPOINT. The log proves that's not the case — the CLI always uses `--entrypoint /bin/sh` regardless of `overrideCommand`. The `overrideCommand` setting only controls what **command** (CMD) the CLI passes:
- `true` (default): `-c "while sleep 1000; do :; done"` → container stays alive
- `false`: `-c "echo Container started"` → container exits immediately

With the ENTRYPOINT being always overridden, `overrideCommand: false` resulted in a container that dies as soon as PID 1 finishes echoing. The correct fix is to use the default (`true`) so the CLI's own keep-alive mechanism keeps PID 1 running.
